# 模型广场分组监控

模型广场分组监控向用户展示已配置分组的探测状态，入口为 `/group-monitor` 和 `/api/pricing/group-monitor`。管理员在 `/channel-monitor` 的分组监控设置中配置分类、分组、探测模型、间隔和展示窗口。

## 管理视图

Root 管理接口提供配置、候选模型、总览、手动执行和执行历史。配置使用 revision；探测间隔为 30 到 86400 秒，展示窗口至少覆盖两个探测周期，每组配置一个具体文本 `probe_model`。重复手动执行返回冲突。

配置采用“分类 → 分组”两级管理：先创建并命名分类，再在分类下添加监控分组。分类名称去除首尾空白后须为 1 到 64 个字符且不能重复，最多 100 个分类、合计 100 个监控分组。空分类也能独立保存；分类支持重命名和上移、下移，分类下的分组支持单独排序、移除及移动到其他分类。分类内还有分组时，须先移走或移除分组才能删除分类。修改分类不删除历史探测记录。

管理接口通过 `categories` 保存分类名称及顺序，`groups` 中的 `category` 指向已创建分类。保存时按分类顺序排列分组，并保留分类内的分组顺序。用户页面按相同顺序展示所有已配置分类和监控分组，空分类显示“此分类暂无监控分组”。旧配置按原有分类归入对应分类，没有分类的分组归入“未分类”；首次读取不写数据库，保存时转换为新格式。旧客户端不传 `categories` 时保留已有分类，包括空分类。

Worker 每个逻辑分组每轮只执行一次探测；上游失败可以在物理成员之间重试，但管理员执行记录保留最终逻辑结果和实际渠道。下一监测周期开始时仍未完成的分组会记录 timeout，已完成的分组结果保持不变；timeout 显示为黄色告警，且计入失败统计。结果包括 success、upstream_failure、rate_limited、local_failure、unavailable、timeout 和 skipped；skipped 不计入成功率。探测成本归属实际物理渠道。

探测请求根据渠道类型使用对应的 API 端点：Anthropic 渠道使用 Messages API (`/v1/messages`)，其他渠道使用 Responses API (`/v1/responses`)。系统自动选择适配的端点类型，无需手动配置。

分组探测执行前检查模型名称是否合法、是否仍在所选渠道的支持范围内，并过滤非文本模型。探测校验不使用渠道类型白名单，Claude 模型可以通过 Messages 端点参与文本探测。

## 用户视图

用户接口遵循 pricing 模块的启用和登录要求，以监控配置作为展示清单；访客、普通用户、管理员和超级管理员均看到相同的分类和监控分组，没有管理员预览分支。不会再按“用户可用分组”或分组倍率是否已配置过滤监控卡片。接口返回有序 `categories`，以及各分组的 group、可选的 category、initial、status、probe_model、latest_first_token_ms、success_rate、group_ratio、last_finished_at 和 recent_window。分组倍率沿用当前账号的实际倍率计算。不会返回渠道 ID、Key、成本、错误详情、租约或管理员配置；未加入监控配置的分组和历史记录也不返回。

状态包括 unconfigured、paused、pending、healthy、unavailable、unhealthy、rate_limited 和 stale。已配置的分组始终保留状态卡片及历史结果。渠道停用或模型能力关闭不使监控配置失效，仍可保存该目标；没有启用成员能力时，管理及用户视图显示 unavailable（暂不可用）。模型或分组关系确实移除、渠道删除或模型不支持文本探测时，管理接口显示 unconfigured，用户侧显示 unavailable。监控关闭时用户侧优先显示 paused（已停用）。

分组监测沿用业务选路、重试时的稳定性降级放宽和 429 冷却兜底。现有选路最终没有候选时，本轮记录 `unavailable / no_available_route`，不请求上游，计入失败统计；不会因渠道禁用而记为模型失效并跳过。流量暂停、稳定性等运行策略造成的无路由由监测周期更新。该判断不依赖测试账号，也适用于全部成员禁止自动探测的分组；若仍有业务路由，则继续跳过自动主动探测并使用原有 Redis 业务周期数据。历史业务周期保留其指标与时间，不覆盖当前不可用或配置失效状态，也不以较旧周期覆盖最近的无路由结果。

普通用户请求继续使用原有无渠道错误链路。渠道状态探测、模型检测及智能调度恢复探测保留各自的独立执行资格、自动探测开关和恢复条件；分组不可用不等于这些检测必须失败，检测成功也不直接解除手动禁用或暂停流量。

保存监控配置只决定状态展示，不授予模型调用权限，也不改变令牌分组、用户可用分组或计费配置。用户重新进入展示页、从其他标签切回展示页时会重新读取配置，避免 30 秒缓存期内仍显示保存前的分类。

管理 API 前缀为 `/api/channel_monitor/group_monitor`：

- `GET /settings`
- `PUT /settings`
- `GET /overview`
- `POST /run`
- `GET /executions`

用户 API 为 `GET /api/pricing/group-monitor`。Worker 扫描间隔由 `CHANNEL_GROUP_MONITOR_SCAN_INTERVAL_MS` 控制，默认 `1000` 毫秒，范围 `200..30000`。

## 分组独立启停

“分类与分组”中的每个分组有 `enabled` 开关，保存后生效。关闭保留模型、分类、排序和管理员执行记录，清空展示统计，定时及手动探测都跳过；重新启用恢复参与。全部分组关闭时不再安排定时任务，清除排队手动任务并禁用“立即探测”。

全局周期开关只控制定时执行，关闭后仍可手动探测已启用分组；页面状态按当前启停配置展示。已经发送的请求正常收尾。旧配置省略单组 `enabled` 时默认开启，显式 false 保留。

## 缓存率与展示周期

“展示设置 → 显示缓存率”默认关闭。开启后，分组监控在成功率旁同时显示用户 API Key（调用令牌）的最高缓存率与平均缓存率。先按每个 Key 汇总本分组、当前展示周期内的有效流式业务请求：缓存读取 Token 总和 ÷ 总输入 Token 总和 × 100%；再取各 Key 缓存率的最高值与等权算术平均值。分组监控继续应用配置的上下文下限。非流式请求、探测和缺少有效总输入的请求不参与计算。

同一个 Key 跨渠道、模型和日期的 Token 先合并，再计算缓存率；在其他分组的请求不混入。没有有效样本或无法识别 Key 的数据不参与这两个指标；有效零命中的 Key 以 0% 参与平均。例如两个 Key 分别为 20% 和 50%，展示最高 50%、平均 35%，不按两个 Key 的请求量或输入 Token 量加权。接口新增 `cache_rate_max` 和 `cache_rate_average`，只返回统计值，不返回 Key 身份。原 `cache_rate` 字段保留按输入 Token 加权的整体缓存率，供旧客户端兼容。

总输入包含普通输入、缓存读取和缓存写入，不含输出；缓存写入只计入分母，不算命中。例如普通输入 100、缓存读 600、缓存写 300 的请求，缓存率为 60%；只有缓存写入、没有缓存读取的有效请求会计入分母，缓存率为 0%。

统计时间跟随配置的分钟/小时/天展示周期，最长支持 30 天，不查询数据库日汇总。业务事件经 Redis Stream 消费后，只增量更新所属分组、对应用户 Key 的 Token 累计值、缓存率排序和缓存率之和；读取最高值与等权平均值无需遍历所有 Key。旧桶退出窗口时分批扣减，每批最多处理 128 个 Key，任务中断后可继续，不重复扣减。

后台约每 5 秒检查一次变化：新事件只刷新所属分组；其他分组复用已生成的结果。展示窗口滚动、探测状态到期，或说明、倍率、被动监控结果等发生变化时更新相应展示；没有变化时只给现有快照续期。访问页面只读取快照，不现场汇总。渠道与路由元数据使用 15 秒短缓存，后台发现变化后更新快照；保存监控配置时绕过该缓存。

主动探测仍按照配置的探测间隔执行，业务请求的缓存统计则随 Stream 事件持续累计，两者互不等待。例如探测间隔为 5 分钟时，探测结果按该间隔产生，但期间的新缓存样本仍能在后台下一次检查后反映到快照。保存监控配置后立即尝试生成初始快照，后续事件再逐步补充统计。

“缓存率最小上下文（K tokens）”对应 `cache_min_context_k`，支持 `0..1000` 的整数，默认 `0` 统计全部有效流式请求。正数只统计总输入上下文大于或等于该下限的流式业务请求，`1 K = 1000 tokens`；归一化总输入包含缓存读取和写入，不含输出。保存监控配置后切换统计版本，清理旧汇总并重新累计；排队、重试或回放中的旧版本事件不能进入新统计。其他节点约 5 秒内同步版本，同步前的旧版本样本会被排除。分组的探测模型成员关系变化也会在后台刷新时重置统计；说明、倍率和渠道可用状态由后台刷新到快照。

升级或 Redis 数据丢失后从新版本开始累计，不导入数据库中的旧执行记录、日汇总或旧版 Stream 事件。窗口内尚无有效样本时显示“暂无数据”。

零命中显示 0.0%，无有效 Key 样本显示“暂无数据”。仅有旧版整体缓存率时，不将其作为最高值或等权平均值。Redis 不可用或快照过期时接口返回 503；快照有效期最长为 30 秒，临近状态到期或窗口边界时会缩短。没有新请求时后台续期可维持快照有效，后台停止后则自动过期，不会持续显示旧的正常状态。页面每 10 秒刷新，在刷新失败后隐藏旧数据。关闭显示开关时不返回缓存率字段。

保存配置时，省略 `show_cache_rate` 或 `cache_min_context_k` 会保留已有值，显式 `0` 清除阈值。关闭缓存率时禁用阈值输入但保留配置。保存需携带当前 revision，避免覆盖其他人的修改。

## 历史存储与清理

分组展示统计全部保存在独立 Redis 命名空间中。探测桶的保留期覆盖配置窗口并留出一个桶的余量；缓存统计桶由后台扣减完毕后删除，避免先过期导致无法准确移除窗口累计值。即使没有新请求，页面统计也会随窗口滚动；后台停止期间保留待扣减的桶，恢复后继续清理。各用户 Key 只累计 Token 总数，不额外保存业务请求明细。配置变化会清理旧统计版本的桶、去重记录、最新状态和快照。

分组事件去重按事件创建小时分桶，保留 48 小时并留出最多一小时的分桶余量，不再随 30 天展示窗口保留全部事件 ID。创建超过 48 小时的排队或重放事件不再进入分组统计，防止去重记录过期后重复累计；已经累计的统计值仍按展示窗口保留。此限制只影响分组展示统计，不改变渠道监控其他消费步骤。统计内存仍随活跃 Key 数、分组数和窗口桶数增长，去重内存仍随最近 48 小时的有效事件量增长。当前监控分组上限仍为 100。

监控配置与管理员探测执行记录仍保留数据库持久化。每个逻辑探测结果与对应的待发送事件在同一事务提交，经现有 Outbox 转发到 Redis Stream；物理重试不会重复增加逻辑探测成功率。管理员执行明细继续由“分组监控记录保留天数”控制，默认 7 天，其清理不影响已累计的 Redis 展示窗口。业务日统计保留配置也不再决定分组监控的展示范围。
