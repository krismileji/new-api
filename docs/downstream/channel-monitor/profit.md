# 利润统计

利润统计按「用户最终扣费 − 渠道总成本」计算人民币账面利润。渠道监控总览在「今日已结算成本」卡片内合并展示成本和利润，并展示用户扣费与利润率；今日成本、扣费、利润及成本分类使用同一次数据库核对结果，刷新失败时保留上次结果并提示。总览成本卡片仅展示今日数据，不显示昨日对比，也不为昨日对比额外查询两日成本摘要。点击卡片打开利润分析，包含成本、利润和扣费汇总及明细。渠道列表按渠道显示今日利润；独立查询的渠道行刷新失败时也会提示保留上次核对结果，并提供重试按钮，首次加载失败不会显示为零利润。打开利润分析可查看日期趋势，并按渠道、用户、API Key 和模型下钻。渠道行里的成本入口仍打开对应成本明细。

扣费按钱包或订阅分别汇总。本平台按 1 额度单位 = 1 人民币记账，即使用户界面显示美元符号，收入仍为「实际扣费额度 ÷ 每单位额度」，不乘美元兑人民币展示汇率。例如日志扣费 7，利润统计收入也为 7。每单位额度使用请求保存的快照。订阅显示额度消耗的名义金额，不代表订阅销售回款；本页利润属于账面毛利。退款和异步任务补扣会修正原请求的收入记录。渠道成本包含业务请求、失败重试、探测和模型检测成本，按物理渠道归属。

收入记录从启用该功能后开始累计，不会从历史消费日志回填。所选范围包含启用前的日期时，汇总利润金额和利润率显示「—」，注明「历史收入缺失」；超出保留范围或没有可用结果时也保留占位。渠道、用户、API Key 和模型等跨日汇总按整个所选范围判断，不以最后一条记录的日期代替统计范围。每日趋势独立判断：缺失或过期日期保留占位，之后仍在保留范围内的完整日期可展示已确认或暂估利润。扣费或退款尚未确认、成本尚未入账、成本未解析或统计覆盖不完整时，直接展示「已确认用户扣费 − 已结算渠道成本」的差额及利润率，金额标注「暂估」。待确认收入和未解析成本暂未计入，补账后金额可能增加、减少或转为亏损。总览、渠道列表、下钻明细和每日趋势使用同一规则；趋势包含暂估值时图例注明「利润（含暂估）」，每日数值分别标注。收入和成本完整入账后自动取消暂估标记；只有已确认的负利润使用亏损颜色。「仅看已确认亏损」只筛选已确认的亏损行，逐级展开的模型、用户和 API Key 明细沿用该筛选。顶部汇总和趋势始终保留当前筛选范围内的完整结果。Midjourney 的钱包、令牌、用量、收入和已扣额度在扣费或退款时共同提交；退款暂时失败的任务即使已经完成，也会继续尝试退款，重复处理不会重复退钱。

总览和利润分析将待处理原因压缩为一行，例如「成本入账中 · 扣费/退款待确认 18 笔 · 未解析成本 1,778 笔」。利润分析保留「刷新核对」入口，详细口径、历史缺失和记录缺口的处理提示收进默认折叠的「统计说明」。首次启用当天不会通过等待或刷新补齐历史；说明中展示北京时间下的首个完整统计日，到达该日期后可点击「仅看完整日期」，将查询范围切换到该日起至今天（最多最近 90 天）。这只排除启用前的时间，不会消除写入失败、未解析成本等其他缺口。

当天即可核对新收入是否写入：使用独立 API Key，在利润明细中记录当前用户扣费，完成一笔正常付费调用，再点击「刷新核对」，比较该 Key 的用户扣费增量与消费日志中该请求的最终扣费，按平台 1:1 口径直接比较金额，并排除其他并发请求的扣费。刷新会同时更新当前打开的利润汇总、趋势和下钻明细。探测和模型检测只有成本，不产生用户收入。收入增长仅证明收入记录正在写入；判断利润是否正确还需核对对应成本，并确保所选范围的利润已经确认。

收入明细跟随成本保留期限清理。历史过期后，异步任务仍可退款或补扣；资金调整不会重建已清理的收入和成本报表。超出保留范围的历史、成本队列积压、无法读取队列或隔离成本事件未处理时，受影响范围不会显示为已确认利润。可识别的队列事件和写入缺口按北京时间日期及物理渠道隔离，不影响无关渠道。新增收入写入缺口会关联成本事件：结束日尚未知时，该渠道从缺口发生日起保持待确认；成本入账后，缺口归入最终成本日，之后完整日期可独立确认。按日趋势独立确认各天，即使所选范围包含启用日，完整日期的利润和亏损筛选仍可使用。无法识别归属的事件、无法读取队列或超过单次检查上限的积压仍保守地标记待确认。

普通请求归入成本结算当天（北京时间）；收入记录与成本并发入账时，会等待该笔成本事务完成后确认入账状态和归属日期。跨日实时会话的逐次扣费在成本入账时统一归入会话结束日；异步任务的补扣与退款修正任务提交日。异步任务的初始差额与任务插入共同提交，轮询只能读取已完成资金调整的任务额度。如果轮询先于后续收入校正完成退款或补扣，校正时会读取数据库中的最新任务额度。Midjourney 退款修正收入，成本仍沿用渠道已记录成本。已持久化的收入写入缺口不会因刷新或重启消失，也不会因其他请求成功而被当作补齐。

从使用全局缺口标记的旧版升级时，旧缺口保守地保留至升级当天结束，之后完整日期可独立确认。旧版无法确定缺失记录的渠道和结束时刻，因此升级不会将这段历史直接改成已确认。先停止旧版本节点，再由新版主节点完成迁移，随后启动新版从节点。

利润记录启用后，钱包扣费和退款直接写入数据库；即使开启批量更新，钱包余额也不再等待内存批次落库，其他用量统计仍沿用批量配置。钱包及令牌额度读取沿用缓存优先方式，缓存命中不因利润记账额外查询数据库，未命中或读取失败时再回源。资金变动与额度缓存修复任务共同保存，结算后尝试清理缓存；Redis 故障期间允许显示及额度判断短暂滞后，恢复后由后台继续清理。缓存回填会检查读取前的版本，已失效的旧快照不能再次写入。正常缓存命中不增加数据库查询；未命中时增加一次 Redis 版本读取。缓存恢复依赖主节点调度，不保证在固定时间内完成，也不以恢复失败为由重复扣费或退款。普通请求、实时分次扣费及违规费用在创建收入记录时保存最终结算指令；最终资金差额、令牌差额与收入确认共同提交。结算暂时失败时，由现有系统任务调度每分钟重试已保存的指令，利润保持待确认，资金提交后再确认收入。待恢复资金指令不会被报表历史清理删除。主节点必须运行系统任务调度；资金恢复任务类型为 `channel_monitor_income_recovery`，成本归属恢复为 `channel_monitor_income_cost_recovery`，额度缓存恢复为 `channel_monitor_funding_cache_recovery`，失败请求及本地响应退款恢复为 `channel_local_response_refund`。四类任务分别调度并持有独立租约，一类任务超时不会耗尽其他任务的执行预算；单条资金、成本、缓存或退款恢复都有独立等待上限，并保存各自的扫描进度；本轮扫描范围固定，失败记录留待下一轮重试，避免持续占据队首或新记录不断推迟旧记录。资金、成本与退款扫描进度保存在数据库，缓存扫描进度保存在 Redis；扫描进度独立于失败记录，重启后可继续，Redis 游标丢失时重新扫描，数据库中的修复指令仍保留；共享数据库或 Redis 本身不可用时仍需等待基础服务恢复。

预扣金额、资金来源和令牌归属与钱包/订阅/令牌的扣减在同一事务保存为 `reserved`；补充预扣同时修正该记录。预扣事务失败不会留下半笔扣款，同一请求标识不能再次预扣。在最终用量及结算指令保存前进程退出时，保留已预扣的资金，收入与利润保持待确认，后台不会自动退款或按预扣确认收入；零预扣也保存请求记录。未结束的预扣记录不会随报表历史清理删除。正常结算转为已有的最终结算恢复流程；明确失败或本地响应的退款通过持久化退款记录完成，退款与预扣记录关闭共同提交。退款恢复每批最多 45 秒，单条最多 5 秒；失败指令保留，后续批次按持久扫描进度继续处理其他记录。实际退款不接管其他请求的待写额度，也不获取额度批次锁。入队时需要同步的内存预扣与退款指令共同提交；提交结果不确定时，这份批次从普通写入器中隔离，以固定标识继续确认，避免重复应用。各节点的既有后台运行模块每分钟重试本机未确认的入队，整批最多 45 秒、单条最多 5 秒；新请求产生的批次独立处理。数据库中已保存的退款指令可在进程重启后继续恢复。尚未提交的纯内存批次仍沿用批量模式的进程退出边界，不把内存状态当成持久资金依据。

新增订阅预扣会保存所属额度周期及该周期内的补扣金额；明确失败后只退回当前周期实际预扣的额度，已结束周期不冲减新周期用量。退款指令保存必要依据，官方预扣回执后续清理不会阻断该笔退款。旧版本记录若已缺少回执或无法区分跨周期补扣，仍需人工核对，升级不会推测历史扣款。最终结算差额仍沿用官方当前周期调整规则；旧周期请求在重置后结算时，返还差额可能释放新周期额度，这一已知边界等待官方处理。

没有结算指令的历史待确认记录不会仅靠重启补齐，需核对实际资金事实，不能把目标费用直接当作已扣费用。已有保守缺口也不会因为某一条收入恢复而被直接删除。Midjourney 只在资金事务成功后保存已扣额度；任务提前失败时不会随后再扣费。旧任务快照回写不会恢复已经退还的额度。

已保存最终结算指令遇到临时回读或成本归属读取失败时，会保留未确认状态并由后台补齐成本日期；未补齐的收入所依赖的已处理成本事件暂不删除。最终指令尚未保存就发生数据库故障时，保留预扣并记录核对缺口。

旧 `pending` 和中断请求的 `reserved` 可由具备数据库管理权限的运维人员使用 `cmd/channel-profit-reconcile` 核对。命令默认只读列出这两类记录及其资金归属；正在运行的请求也会处于 `reserved`，不能仅凭记录存在或等待时间判断它已中断。显式提供单条核对 JSON 和 `-apply` 才会写入，必须包含 `settlement_key`、`user_id`、`expected_quota`、`expected_updated_at`、已核实的 `net_charged_quota`、`operator` 和 `evidence`。核对 `reserved` 还必须先核实原请求及所属进程已终止、没有异步任务继续结算，再设置 `request_terminated: true`。修正与运维历史共同提交，不改变钱包、订阅、令牌余额，也不自动解除成本或缺口。缺少实际用量或收费证据时继续保留预扣待核对，不能仅将预扣金额当成最终收费。

数据库无法写入时，收入缺口同时保存在持久化目录中，重启时重放，查询时也会直接读取该目录。通过 `CHANNEL_MONITOR_INCOME_GAP_DIR` 指定目录，默认是日志目录下的 `channel-monitor-income-gaps`；容器部署必须将它挂载到持久化存储。多节点部署必须让所有节点的该配置指向同一共享目录，仅共享数据库或 Redis 不足以读取其他节点尚未写库的缺口。目录不可读、标记格式异常或超过读取上限时，网关可继续启动并记录错误，利润保持待确认。清理会分批删除已过期的合法标记，保留异常标记供排查；文件异常不会阻断数据库历史清理。标记随历史保留边界清理，不应手工删除。数据库与该持久化存储同时不可写时，只能保留本机内存告警，无法承诺节点故障后的缺口恢复。

利润分析沿用渠道监控的 Root 管理权限。接口为 `GET /api/channel_monitor/analytics/rows?metric=profit`，支持现有的日期、渠道、用户、API Key、模型和搜索筛选；`sort` 支持 `income`、`cost`、`profit`、`profit_rate`，`only_loss=true` 仅返回已确认的亏损行。统计区间最多 90 天，收入为零时利润率为空。

启用时先让主节点完成数据库迁移，再启动其他节点。可靠成本队列使用现有 `CHANNEL_DAILY_COST_RELIABLE_OUTBOX` 配置，关闭后利润始终标记暂估。功能启用当天因起始时刻之前没有收入记录，利润显示「—」并注明历史收入缺失；之后的完整日期可正常确认。

从旧汇率口径升级时，先停止旧版本节点，再启动新版主节点。主节点会分批将已记录收入按原始扣费额度和当时的每单位额度修正为 1:1；重复启动或中断后重试不会重复扣费。修正保留用户与 Key 归属、统计日期、退款与待确认状态，不修改用户余额、Key 用量和渠道成本，也不会补出启用前缺失的收入。修正完成后再启动新版从节点；未修正的数据库会阻止新版从节点启动，避免继续展示旧换算收入。
