# 模型检测部署与运维

## 集成边界

模型检测使用官方 `gpt56_api_detector` 的 HTTP 接口，检测器必须作为独立服务部署。主系统不修改、打补丁、打包或复制检测器源码，也不接管检测器的发布节奏。检测器应继续按照官方仓库或官方镜像的流程升级，并保留其独立数据卷。

一次检测的调用方向如下：

```text
主系统 Worker -> 官方检测器 /api/*
官方检测器 -> 主系统 /internal/model-detector/v1/responses
主系统固定渠道 Relay -> 目标渠道上游
```

内部 Relay 只注册 `POST /internal/model-detector/v1/responses`。每次执行会冻结渠道、请求模型、申报型号、档位、请求次数预算、检测器地址和短期 Relay 凭证，不能自动改投其他渠道。检测产生的每次上游尝试都会进入成本事件，运行记录同时保存预估成本、已结算成本和无法确认的成本。

## 配置

| 配置 | 用途 | 运行约束 |
| --- | --- | --- |
| 管理端“模型检测统一设置” | 配置检测器地址、检测器访问平台的内部 Relay 地址、定时档位和周期 | 数据库中统一设置是运行时事实来源；仅 RootAuth 保护的统一设置接口回显完整地址，其他摘要接口保持展示字段 |
| `GPT56_DETECTOR_URL` | 首次初始化检测器地址 | 仅在数据库尚无统一配置记录时读取；记录建立后修改环境变量不会覆盖管理端设置 |
| `GPT56_DETECTOR_PROXY_TOKEN` | 可选的检测器反向代理共享凭证 | 主系统以 `Authorization: Bearer <token>` 发送；不得写入应用或代理日志 |
| 管理端“数据保留”中的模型检测历史保留天数 | 检测历史保留天数 | 保存到 `ChannelMonitorModelDetectionRetentionDays`，默认 `30`，允许 `7..180` |

检测器地址保存和连接测试会解析主机名，并要求解析结果全部属于回环或私网地址。主系统发起连接时还会使用检测器专用直连 Transport：每次实际拨号都重新解析主机名，任一候选结果为公网、链路本地、未指定或组播地址时整体拒绝，并直接拨号到已验证 IP；请求 Host 和 HTTPS SNI 仍保留原主机名。该 Transport 不读取环境代理，也不受通用 SSRF 开关影响。生产环境仍应优先使用私网 IP 或受控的内部 DNS。

统一设置中的低、中、高档位只决定定时检测默认档位。管理员发起手动检测时可以为该次轮次单独选择档位，选择结果会冻结在轮次与执行记录中，不会改写定时默认值。高档检测需要单独确认其高成本风险；提交前应检查成本预估，完成后应核对已结算与未决成本。

## 推荐部署

1. 按官方文档独立部署检测器，为其运行数据库或其他运行数据挂载持久卷。
2. 确保主系统能够访问检测器的 `/api/health`、`/api/bootstrap` 和 `/api/detector/*` 接口。
3. 在“模型检测统一设置”保存检测器可访问的内部 Relay 地址。未配置时不会启动新的模型检测任务；不要把仅容器自身可见的 `localhost` 地址传给另一个容器。
4. 内部 Relay 使用内网、网络 ACL 或专用反向代理保护，不应直接暴露到公网。
5. 在管理端输入检测器地址后可直接执行连接测试，无需先保存。测试会验证 `/api/health`、bootstrap 能力和低档估算，且不会写入统一设置或覆盖已保存的服务状态；确认可用后再保存地址。
6. 先对一个非关键渠道执行低档手动检测，确认报告、成本事件和渠道上游账单一致，再启用定时检测。

检测器反向代理如果启用共享凭证，应校验 `GPT56_DETECTOR_PROXY_TOKEN` 对应的 Bearer 值。该凭证保护的是主系统到检测器的请求，不能替代内部 Relay 的网络隔离和任务短期凭证。

## 单实例与多实例

模型检测的短期 Relay 凭证保存在签发它的主系统进程内存中，进程重启后失效，也不会通过数据库或 Redis 共享。数据库租约只能避免任务被多个 Worker 同时持有，不能让其他实例识别该短期凭证。

生产环境首选由单个主系统实例承载模型检测 Worker 和内部 Relay。必须多实例部署时，同一检测会话对内部 Relay 的全部请求必须粘滞到签发凭证的实例。可以使用专用内部 Relay 地址固定到该实例，或在内部负载均衡器上按任务 Bearer 做一致性路由；普通轮询负载均衡不满足要求。

滚动升级主系统时应先等待活动轮次结束，或在管理端取消活动轮次。活动会话存在期间，不得移除或重启签发其短期凭证的实例。

## 地址切换与检测器升级

执行开始后会把检测器地址写入执行快照。活动会话期间保存新地址时，新地址会延后生效；已有执行继续使用旧地址，新执行在活动会话结束并完成地址提升后使用新地址。

主系统当前按官方检测器 `4.1.1` 的接口契约校验版本：`/api/bootstrap` 必须返回配置 Schema `2`，完成报告必须使用报告 Schema `3` 或 `4`；当前已验证的评分版本为 `trusted-fingerprint-v3`。连接测试发现 bootstrap Schema 不兼容时会把检测器状态标为“不兼容”并阻止启动。启动请求会同时发送申报型号和实际请求模型，并保留旧 `model` 字段供 `4.1.0` 读取；完成后还会校验报告中的 `claimed_model`、`request_model` 与执行快照一致。完成报告缺少 Schema、使用不支持的 Schema，或旧检测器无法保留独立请求模型时，主系统会保存脱敏后的原始报告以便排障，但将该执行标记为失败，不解释其中的正常、异常或型号结论；管理端同时显示明确的版本或接口不兼容提示。评分版本未验证或报告记录与原始报告中的版本字段不一致时，管理端也会单独提示，避免把未知字段语义静默当作当前版本结果。

升级检测器时：

1. 暂停定时检测，并等待或取消所有活动轮次。
2. 按官方仓库或镜像说明升级，不修改检测器源码，不把检测器合入主系统镜像。
3. 保留检测器独立数据卷，避免丢失其中断会话和本地历史。
4. 启动后先验证 `/api/health`，再执行管理端连接测试。
5. 执行一次低档手动检测，确认内部 Relay、报告和成本结算正常后恢复定时检测。

不要在检测器仍有运行或中断会话时直接替换实例，否则主系统可能进入 `submission_unknown` 或 `external_session_conflict`，需要人工确认官方会话后取消或重跑。

## 备份与恢复

主数据库备份必须包含以下七张表：

- `channel_model_detection_global_configs`
- `channel_model_detection_configs`
- `channel_model_detection_targets`
- `channel_model_detection_batches`
- `channel_model_detection_runs`
- `channel_model_detection_executions`
- `channel_model_detection_cost_events`

检测器自己的 SQLite 文件（如果官方部署使用 SQLite）或独立数据卷必须单独备份，不能用主数据库备份替代。恢复时应先恢复主数据库和检测器数据，再验证检测器健康与管理端连接。

短期 Relay 凭证只存在内存，无法从任何备份恢复。主系统进程重启、迁移或灾备切换后，应取消或重跑仍处于活动状态的轮次，并核对 `prepared` 或 `pending` 成本事件，避免把未知提交误认为已结算。

## 历史清理

模型检测历史复用渠道监控清理任务。管理端“数据保留”中的模型检测历史保留天数控制轮次、执行和成本事件的保留时间，保存到数据库 option `ChannelMonitorModelDetectionRetentionDays`，默认 `30` 天，范围 `7..180`。清理任务每次运行都直接读取数据库中的最新值，不依赖节点内存中的旧设置缓存。

清理只选择已完成、部分完成、失败、外部会话冲突或已取消的终态轮次。存在 `dispatch_state=prepared` 或 `settlement_status=pending` 成本事件的轮次不会删除，必须先完成核对或结算。清理前仍应保留数据库备份，并监控清理任务是否因时间预算耗尽而续排。

## 监控与告警

至少监控以下信号：

- 检测器 `/api/health`、管理端 `last_checked_at` 和脱敏后的 `last_error`。
- 排队等待时间、活动轮次数和长期停留在 `waiting_detector` 的轮次。
- `submission_unknown` 与 `external_session_conflict`，这两类状态需要人工确认检测器当前会话。
- `prepared`、`pending` 或 `unresolved` 成本事件数量及持续时间，并与渠道上游账单抽样核对。
- 内部 Relay 的 `401`、`403`、`429` 和 `5xx`。连续 `401/403` 通常表示凭证路由错误、过期或实例不粘滞；`429` 需要同时检查任务请求预算和渠道并发限制。
- 主系统 Worker 租约、检测器进程、检测器数据卷空间、SQLite/数据文件健康和备份新鲜度。
- 检测器地址切换是否长期处于待生效状态，以及定时批次是否按配置时间产生。

## 日志与敏感信息

应用日志、访问日志、链路追踪和错误聚合不得记录以下内容：

- 完整检测器 URL。
- 渠道 API Key 或检测器启动请求中的 `api_key`。
- `X-GPT56-Session` 会话 Token。
- 内部 Relay 的短期 Bearer。
- `GPT56_DETECTOR_PROXY_TOKEN` 及其 `Authorization` 请求头。

管理 API 和报告响应已经对上述信息做隐藏或脱敏，但外部反向代理、WAF 和可观测性采集器仍需单独配置 Header 与请求体脱敏。排障时只保留运行 ID、执行 ID、脱敏地址、错误码和时间戳。

## 网络纵深防护

检测器专用拨号器在每次新建连接时重新解析 DNS，先校验全部解析结果，再把底层连接固定到其中一个已验证 IP；混合私网/公网结果会整体拒绝，因此不再依赖保存配置时的一次性解析来防御 DNS rebinding。连接池复用的始终是已经固定目标 IP 的既有连接。

生产环境仍应使用私网 IP 或受控的内部 DNS，并通过出站 ACL、防火墙或容器网络策略只允许访问检测器网段。应用层允许 RFC 私网和回环地址，并不等同于只允许实际检测器所在网段；网络策略仍应显式阻断云元数据地址和其他管理网段。
