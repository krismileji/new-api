# 渠道逻辑归组：使用注意事项

本文是渠道逻辑归组上线后的操作和排障速查。完整设计、验收矩阵和回滚步骤见 [逻辑归组方案](../../../CHANNEL_LOGICAL_GROUP_MONITORING_PLAN.md) 与 [验收/发布清单](logical-group-acceptance-release.md)。

## 1. 功能边界

逻辑归组只共享三类后台能力：

- 智能调度数据、评分、保护状态和组级候选；
- 状态探测的配置、执行范围、状态和探测历史；
- 模型检测的配置、目标、轮次、结论和检测状态。

余额、倍率、成本、性能、成功率、延迟、TPS、失败分类、日志、渠道启停和并发限制仍按物理 `channel_id` 独立处理，不会自动汇总成逻辑组数据。

## 2. 配置前必须确认

1. 归组必须由管理员在渠道监控的“同渠道配置”入口显式完成，系统不会根据名称、标签、Provider、模型列表或 Key 前缀自动归组。
2. 系统只校验规范化后的上游请求地址一致。模型映射、Header、代理、组织、倍率、余额等差异不会阻止保存，管理员需要自行确认这些差异不会影响共享的调度、探测和模型检测。
3. 一个物理渠道最多属于一个逻辑组；同一组至少保留一个成员。已经属于其他组的渠道不能重复加入。
4. 请求地址发生变化时，必须重新检查该渠道是否仍与组内成员一致；地址不一致的修改会被拒绝。

## 3. 三种 weight 不要混用

| weight | 作用范围 | 归组后是否改变 |
| --- | --- | --- |
| 物理渠道 `Channel.Weight` | 普通渠道池的默认选路 | 不改变 |
| 智能调度 `Ability.Weight` | 逻辑组与其他候选之间的调度竞争 | 不被组内 weight 覆盖 |
| 逻辑组成员 `member weight` | 逻辑组被选中后，在多个 Key 之间选具体渠道 | 新增配置，默认 1 |

成员 weight 为正数时按比例倾向分配；存在正数时，0 权重成员不会主动选中；全部为 0 时按平均分配。它不改变余额、倍率、成本或物理渠道默认权重。

## 4. 并发和流量

- 一个请求最终只使用一个物理渠道和一个 Key，不会拆分请求。
- 选出逻辑组后，先按 member weight 选择成员，再调用现有的物理渠道并发租约和释放流程。
- 不新增逻辑组并发计数、并发上限、租约或 Redis 并发键。两个 Key 的并发额度可以同时使用，但每个 Key 仍不能超过自身限制。
- 某个成员并发已满、余额不足或 Key 失效时，只排除该成员；其他健康成员仍可服务。全部成员都不可用时，沿用原有重选或 429 行为。
- 显式指定 `channel_id` 的请求不会跨组改投到其他成员。

## 5. 状态探测和模型检测

- 同一逻辑组、同一目标、同一轮只生成一份共享执行，不会因为成员数量增加而重复请求。
- 实际请求仍通过某一个成员的物理渠道发出，并保留实际 `channel_id`、请求 ID、执行 ID、revision 和脱敏 Key。
- 成本事件仍归属实际成员，不生成逻辑组成本汇总，也不会把一个成员的成本复制到其他成员。
- 成员级 401、余额不足和成员级 429 默认只影响该成员；只有确认是上游账号级限流时才应使用组级保护。
- 共享探测/检测不会绕过成员原有的并发限制。

## 6. 关系变更、删除和历史

- 每次成员变更都会产生新的 `revision`。新任务使用新 revision，已经开始的探测或模型检测使用创建时冻结的成员快照。
- 删除逻辑组只解除成员关系，不删除物理渠道、Key、余额、倍率、成本、日志、探测历史或模型检测执行记录。
- 渠道移出逻辑组后，从该渠道当前视角查询时，旧逻辑轮次不保证自动显示为该渠道的历史；这是查询投影边界，不代表数据被删除或被重新归属。
- 修改组成员、停用组或删除组前，应先确认没有需要持续观察的活动探测/模型检测任务。

## 7. 页面、权限和数据安全

- 入口位于“渠道监控”页面操作区，现有渠道视图、分页、筛选、成本和监控页面不增加父子行或逻辑视图切换。
- 旧渠道 API 的路径和响应结构保持兼容；新增管理 API 仅用于逻辑组查询、预检、创建、替换成员、启停和删除。
- 读取、编辑、删除分别沿用渠道读取、写入和敏感写入权限。
- 页面、接口和执行快照只显示脱敏 Key；地址摘要不能包含 Key 或其他凭据。

## 8. 数据库、缓存和回滚

- 数据库变更是新增逻辑组/成员表和可空的 `channels.logical_channel_id` 等字段，不合并或迁移原有物理监控、成本和余额数据。
- SQLite、MySQL 和 PostgreSQL 的迁移必须使用项目既有 GORM 兼容路径；发布前要确认重复 `AutoMigrate` 不报错、成员唯一约束和 revision 冲突校验正常。
- 滚动迁移期间，如果逻辑组可选表或字段尚未完成，运行时应回退到物理渠道路径，不应阻断普通请求。
- 优先使用 `CHANNEL_LOGICAL_GROUP_ENABLED=false` 做全局回退；也可以将单个逻辑组停用。关闭后新任务回到物理渠道旧路径，已有物理数据保留。
- 回滚时不要直接删表、清空全库 Redis 或手工覆盖 `channels.logical_channel_id`；应通过带 revision 的管理 API 解除关系。

## 9. 上线后的最小检查清单

- 先用两个同地址渠道和一个不同地址渠道验证：同地址可归组，不同地址被拒绝。
- 对比归组前后的余额、倍率、成本、普通监控、日志和并发接口，确认仍按物理渠道独立。
- 观察智能调度是否只出现一个逻辑候选，成员流量是否符合 member weight。
- 将一个成员设为禁用、余额不足或并发满载，确认其他成员仍可用。
- 运行一次状态探测和模型检测，确认每个逻辑目标只有一份执行且成本落在实际成员。
- 修改成员关系并检查 revision：活动任务用旧快照，新任务用新关系。
- 灰度期间重点观察 429、成员选择比例、共享执行重复、过期 revision 写入、缓存刷新失败和成本归属。

发现共享路径异常时，先停用对应逻辑组或关闭全局开关，再保留现场数据进行排查；不要先删除关系或清理监控数据。

## 10. 智能调度开关的影响

“智能调度”开关和“逻辑归组”不是同一个开关，操作时要区分：

- 开启智能调度后，只对已配置策略且命中模型范围的调度池启用智能调度；归组渠道在该调度池中合并为一个逻辑候选，再按 member weight 选择实际 Key。
- 关闭智能调度后，停止新的完整智能调度任务和调度门禁，归组渠道不再参与逻辑组级智能候选合并，回到原有物理渠道选路路径。已有调度状态、样本和历史记录保留，不会删除余额、倍率、成本或监控数据。
- 未配置智能调度策略的分组/模型，本来就一直使用物理渠道选路，开关对它们没有额外影响。
- 智能调度开关不会关闭逻辑组的状态探测或模型检测共享；这两项仍由逻辑组状态和 `CHANNEL_LOGICAL_GROUP_ENABLED` 控制。需要完全回退逻辑组共享行为时，应停用逻辑组或关闭该全局开关。
- 保存开关后会刷新运行时配置；正在执行的智能调度任务可能完成当前轮，新请求和后续任务按最新开关处理。
