# 中继重试与错误可见性

## 目的与范围

该功能在上游常规重试机制之外，为特定瞬时错误增加独立重试预算，并记录每次实际上游调用。用户只看到最终失败结果，管理员仍可利用完整尝试日志排查渠道质量。

定向预算只适用于 Chat Completions 和 Responses 中继；任务中继沿用常规重试判断，但共享渠道轮换和最终错误日志处理。

## 定向重试配置

| 环境变量 | 默认值 | 触发条件 |
| --- | ---: | --- |
| `RETRY_400_UPSTREAM_FAILED_TIMES` | `1` | HTTP 400 且错误文本精确为 `Upstream request failed` |
| `RETRY_502_TIMES` | `1` | HTTP 502 |
| `RETRY_503_TIMES` | `1` | HTTP 503 |
| `RETRY_524_TIMES` | `1` | HTTP 524 |

负数会按 `0` 处理。四项预算彼此独立，也不消耗常规 `RETRY_TIMES` 预算。是否执行其他常规重试仍由系统的自动重试状态码和错误码规则决定。

环境变量在进程启动时读取，修改后需要重启实例。

## 渠道路由

发生可重试错误后，请求会优先对当前渠道进行一次针对性重试。渠道连续失败后会被本次请求临时排除，再从符合模型和分组条件的其他渠道中选择。

若候选渠道已轮换完毕，路由状态会从首个候选重新开始，避免一次请求因临时排除集合耗尽而直接失去所有可用渠道。自动分组在重新开始时同步重置组选择索引。

显式锁定渠道、指定渠道以及没有替代渠道的场景仍遵守原有约束，不会越权选择其他渠道。

下游客户端取消请求时，通过公共 HTTP 中继路径发送的上游请求会随请求 Context 一并取消；所有文本和任务中继均不会继续消耗定向或常规重试预算。

## 错误日志

每次将继续重试的渠道错误都会以 `is_retry_attempt=true` 记录；最终仍失败时另行记录最终错误。这样可以同时得到两种统计口径：

- 实际调用口径：包含重试过程中的失败，用于评估上游真实稳定性。
- 最终结果口径：排除中间重试失败，用于表示用户最终看到的成功或失败。

普通用户的日志查询会过滤中间重试记录，并把错误正文收敛为可识别的 HTTP 状态码；管理员日志保留排障所需的渠道、错误类型、错误码和受保护调试信息。

## 与渠道监控的关系

渠道监控的成功率和稳定性保护使用“实际调用口径”，因此一次最终成功的请求如果经历过失败重试，仍会降低对应渠道的实际成功率。最终成功率则用于观察请求对用户的最终影响。

单渠道并发限制也复用同一套路由排除机制。渠道满载时会先排除该渠道并尝试其他候选，详见 [测试与并发限制](../channel-monitor/testing-and-concurrency.md)。

## 关键实现

- `controller/relay_retry.go`：定向重试预算。
- `controller/relay_retry_routing.go`：同渠道重试、排除和候选重启。
- `controller/relay.go`：文本与任务中继集成、最终错误记录。
- `model/log.go`：重试标记和用户日志过滤。
- `setting/operation_setting/status_code_ranges.go`：常规状态码重试规则。
