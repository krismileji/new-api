# 中继重试与错误可见性

## 目的与范围

中继失败后的重试统一使用系统设置中的常规重试预算和状态码规则。失败渠道会在本次请求中立即排除，后续尝试只选择其他符合模型、分组和路由条件的渠道，避免慢渠道被重复调用而放大尾延迟。

Chat Completions、Responses、其他文本中继和任务中继共享渠道排除及最终错误日志处理。任务中继继续使用自身的错误判断规则。

## 重试配置

中继没有额外的下游环境变量重试预算。管理员通过以下系统设置控制重试：

- `RetryTimes`：首次请求失败后最多允许的重试次数。
- `AutomaticRetryStatusCodes`：文本中继允许自动重试的 HTTP 状态码和区间。

默认自动重试状态码为 `100-199,300-399,401-407,409-499,500-503,505-523,525-599`。默认不重试 `2xx`、`400`、`408`、`504` 和 `524`；`504` 始终禁止重试。错误码为 `bad_response_body` 或显式标记为 `skip_retry` 的错误也不会重试。

任务中继在 `RetryTimes` 预算内重试 `429`、`307`、除 `504` 外的 `5xx` 及其他符合其现有判断规则的非本地错误，不读取 `AutomaticRetryStatusCodes`。

## 渠道路由

错误满足重试条件时，当前失败渠道会立即加入本次请求的排除集合。下一次尝试从其余符合模型、分组、优先级和请求路径条件的渠道中选择，不会先在同一渠道上重复请求。

候选渠道全部排除后停止重试，并向客户端返回最后一次实际上游调用的错误，不会清空排除集合后重新回到已失败渠道。

显式指定渠道和任务锁定渠道仍遵守原有约束，不会越权切换其他渠道。

渠道亲和沿用官方规则：

- `skip_retry_on_failure=true` 时，亲和渠道失败后立即停止重试。
- `skip_retry_on_failure=false` 时，符合常规重试规则的错误会排除当前亲和渠道并选择其他渠道。
- `switch_on_success=true` 时，其他渠道重试成功后会把亲和绑定更新为成功渠道。

下游客户端取消请求时，通过公共 HTTP 中继路径发送的上游请求会随请求 Context 一并取消，文本和任务中继均不会继续消耗重试预算。

单次上游调用的响应头等待时间由 `RelayResponseHeaderTimeoutSeconds` 控制。设置为 `0` 表示不限制；需要限制慢渠道尾延迟时应配置合理的非零值。

## 错误日志

每次将继续重试的渠道错误都会以 `is_retry_attempt=true` 记录；最终仍失败时另行记录最终错误。这样可以同时得到两种统计口径：

- 实际调用口径：包含重试过程中的失败，用于评估上游真实稳定性。
- 最终结果口径：排除中间重试失败，用于表示用户最终看到的成功或失败。

普通用户的日志查询会过滤中间重试记录，并把错误正文收敛为可识别的 HTTP 状态码；管理员日志保留排障所需的渠道、错误类型、错误码和受保护调试信息。

## 与渠道监控的关系

渠道监控的成功率和稳定性保护使用“实际调用口径”，因此一次最终成功的请求如果经历过失败重试，仍会降低对应渠道的实际成功率。最终成功率用于观察请求对用户的最终影响。

单渠道并发限制复用同一渠道排除集合。渠道满载时会排除该渠道并尝试其他候选，详见 [测试与并发限制](../channel-monitor/testing-and-concurrency.md)。

## 关键实现

- `controller/relay_retry_routing.go`：失败渠道排除和候选耗尽判断。
- `controller/relay.go`：文本与任务中继集成、最终错误记录。
- `model/log.go`：重试标记和用户日志过滤。
- `setting/operation_setting/status_code_ranges.go`：常规状态码重试规则。
