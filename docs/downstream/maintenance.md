# 文档维护约定

## 文件组织

每个独立功能必须使用专属子目录，并以 `README.md` 作为功能入口。功能较大时在该目录继续按稳定业务主题拆分多份文件；不要创建只有标题的占位文件。

文件名使用小写英文和连字符。面向使用者的正文使用简体中文，代码标识、接口路径、配置键和环境变量保留原样。

渠道监控的页面、接口、任务、模型、成本、测试和并发控制都归入 `channel-monitor/`，即使实现代码分布在 `controller/`、`service/`、`model/` 和 `web/`。

## 功能文档应包含的内容

根据功能实际情况记录以下信息：

- 功能目的和明确边界。
- 用户角色、页面入口和典型操作流程。
- API、系统选项、环境变量及默认值。
- 数据表、缓存、日志、定时任务和迁移影响。
- 权限、安全、计费和失败处理规则。
- 关闭、回滚或恢复方式。
- 关键实现文件和验证命令。
- 与上游实现的差异及合并冲突关注点。

## 变更流程

新增功能时，先在 [功能总览](feature-catalog.md) 增加条目，再创建功能目录和入口 `README.md`。功能演进时直接更新原目录中的专题，不按提交日期复制多份功能说明；只有确实需要保留历史决策时才新增设计记录。

功能下线后不要直接删除记录。先将状态改为“已下线”，说明数据清理、配置兼容和替代方案；确认不再需要追溯后再单独删除文档。

同步上游前后应复核专题文档列出的关键实现文件。若上游已经提供等价能力，应说明二开逻辑是继续保留、缩减为适配层，还是完成迁移。

## 推荐模板

新专题可以从以下结构开始，并删去不适用的章节：

```markdown
# 功能名称

## 目的与范围

## 使用入口

## 行为规则

## 配置与接口

## 数据与安全

## 运维与恢复

## 实现位置

## 验证

## 上游同步关注点
```

## 完成检查

提交前检查相对链接可用，接口和配置名与代码一致，并运行：

```powershell
git diff --check
git diff --stat
```
