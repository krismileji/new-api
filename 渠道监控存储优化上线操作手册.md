# 渠道监控存储优化上线操作手册

本次是停机一次性切换，不兼容旧代码、旧表、旧配置和旧渠道监控历史。Redis 必须为 6.2+ 并支持 XAUTOCLAIM。

执行前先替换以下占位符：

- MYSQL_HOST：MySQL 主机
- MYSQL_PORT：MySQL 端口
- MYSQL_USER：MySQL 用户
- DATABASE_NAME：生产数据库名
- REDIS_CONN_STRING：生产 Redis 完整连接串，必须包含正确逻辑库号

MySQL SQL 在同一个明确的目标库会话中执行。Redis 操作通过 Redis 管理界面手动执行。本文中的 DROP、DELETE 和 Redis key 删除都由上线人员执行，本文不会自动执行任何生产清理。

## 1. 停止服务

1. 关闭负载均衡、网关和其他入口流量。
2. 停止全部 API 节点、任务节点、渠道监控 worker。
3. 停止自动拉起、滚动发布和健康检查重启。
4. 确认没有旧进程继续连接 MySQL 或 Redis。
5. 确认 Redis key channel_monitor:v1:consumer:heartbeat 不再刷新。

在单节点验收完成前，不要启动其他节点，也不要恢复入口流量。

## 2. MySQL 连接和前置检查

使用明确的生产连接参数进入数据库，密码使用交互输入：

~~~bash
mysql --host=MYSQL_HOST --port=MYSQL_PORT --user=MYSQL_USER --password --database=DATABASE_NAME
~~~

进入 MySQL 后执行：

~~~sql
SELECT
    @@hostname AS mysql_host,
    @@port AS mysql_port,
    DATABASE() AS current_database,
    @@version AS mysql_version,
    @@read_only AS read_only,
    @@super_read_only AS super_read_only;

SELECT
    ID,
    USER,
    HOST,
    DB,
    COMMAND,
    TIME,
    STATE,
    LEFT(INFO, 200) AS INFO
FROM information_schema.PROCESSLIST
WHERE DB = DATABASE()
  AND ID <> CONNECTION_ID()
ORDER BY TIME DESC;
~~~

只有确认 current_database、主机和端口都正确，且没有应用写入会话后才能继续。

## 4. MySQL 备份

优先创建云数据库快照。没有快照时，在应用完全停止后执行：

~~~bash
mysqldump --host=MYSQL_HOST --port=MYSQL_PORT --user=MYSQL_USER --password \
  --single-transaction --quick --routines --triggers --events --hex-blob \
  --set-gtid-purged=OFF DATABASE_NAME > new-api-before-channel-monitor-cleanup.sql
~~~

备份完成后执行非空和校验检查：

~~~bash
test -s new-api-before-channel-monitor-cleanup.sql
sha256sum new-api-before-channel-monitor-cleanup.sql
~~~

记录备份时间、文件位置或快照编号、文件大小和 SHA-256。备份失败、文件为空或校验值未保存时停止上线。

## 7. Redis 管理界面清理前检查

1. 使用生产 REDIS_CONN_STRING 对应的主机、端口、TLS、用户名和逻辑库号登录 Redis 管理界面。
2. 确认 Redis 版本至少为 6.2。
3. 确认当前逻辑库号与应用配置完全一致。
4. 确认全部应用和任务节点已经停止。
5. 在 key 浏览器中按精确前缀 channel_monitor:v1: 搜索。
6. 记录搜索结果数量，并确认 channel_monitor:v1:consumer:heartbeat 不再刷新。

搜索结果只允许属于以下清单：

- channel_monitor:v1:events
- channel_monitor:v1:aggregator:lease
- channel_monitor:v1:consumer:heartbeat
- channel_monitor:v1:observability
- channel_monitor:v1:projection:route: 开头的 key
- channel_monitor:v1:projection:dashboard: 开头的 key
- channel_monitor:v1:projection:cost: 开头的 key
- channel_monitor:v1:projection:dedup: 开头的 key
- channel_monitor:v1:projection:shared:event: 开头的 key
- channel_monitor:v1:projection:runtime:event: 开头的 key
- channel_monitor:v1:projection:schedule:event: 开头的 key

发现清单外 key、逻辑库不一致、Redis 版本不足或心跳仍刷新时停止操作。

## 8. Redis 管理界面手动删除

在 Redis 管理界面中删除第 7 节搜索到的全部渠道监控 key：

1. 删除 channel_monitor:v1:events。它是 Stream；删除该 key 后，消费组 channel_monitor:v1:aggregators 和 pending 信息会一起删除。
2. 删除 channel_monitor:v1:aggregator:lease。
3. 删除 channel_monitor:v1:consumer:heartbeat。
4. 删除 channel_monitor:v1:observability。
5. 删除所有 channel_monitor:v1:projection:route: 开头的 key。
6. 删除所有 channel_monitor:v1:projection:dashboard: 开头的 key。
7. 删除所有 channel_monitor:v1:projection:cost: 开头的 key。
8. 删除所有 channel_monitor:v1:projection:dedup: 开头的 key。
9. 删除所有 channel_monitor:v1:projection:shared:event: 开头的 key。
10. 删除所有 channel_monitor:v1:projection:runtime:event: 开头的 key。
11. 删除所有 channel_monitor:v1:projection:schedule:event: 开头的 key。

管理界面支持按前缀批量选择时，可以筛选 channel_monitor:v1: 后批量删除，但必须先确认结果全部属于上述清单。管理界面不支持批量删除时，按搜索结果逐页删除。

消费组中的消费者名称不是独立 key，不需要单独删除。不要删除 channel_monitor:v1 之外的 key，也不要使用 FLUSHDB、FLUSHALL 或清空数据库功能。

## 9. Redis 删除后核验

1. 再次按精确前缀 channel_monitor:v1: 搜索，结果必须为 0。
2. 单独搜索 channel_monitor:v1:events，必须不存在。
3. 确认管理界面中其他业务 key 仍然存在。
4. 清理完成前保持全部应用停止。

## 10. 部署并启动一个节点

所有节点部署同一个新版本。每个节点配置：

~~~text
REDIS_CONN_STRING=<生产 Redis 完整连接串，包含正确逻辑库号>
CHANNEL_MONITOR_CONSUMER_ID=<每个节点唯一值>
~~~

先只启动一个节点，确认启动日志显示：

1. MySQL 迁移成功。
2. Redis Stream 和消费组初始化成功。
3. XAUTOCLAIM 检查成功。
4. 没有数据库、Redis、缺表或索引错误。

启动失败时保持其他节点停止，不绕过 Redis 或迁移检查。

Redis 启动后在管理界面检查：

1. channel_monitor:v1:events 已重新创建，类型为 Stream。
2. Stream 的消费组中存在 channel_monitor:v1:aggregators。
3. channel_monitor:v1:consumer:heartbeat 已重新创建并持续刷新。
4. 产生监控事件后，channel_monitor:v1:observability 和 projection 类 key 开始出现。
5. 如果管理界面不展示消费组，在应用启动日志或渠道监控实时状态中确认 Redis 可用且消费者正在运行。

在管理端重新配置倍率监控、状态探测、模型检测和智能调度。数据保留先使用：

## 13. 单节点验收

入口流量继续保持关闭，在管理端手动执行一次完整调度，确认：

1. 调度任务最终成功。
2. channel_smart_schedule_execution_details 每个任务只有一行记录。
3. 快照为 gzip，详情页面可以正常查看、筛选、排序和分页。
4. 分钟指标、Redis 投影和清理任务正常产生或运行。
5. Redis pending 不持续增长。
6. 健康度变化仍触发完整调度，没有增加节流或改成局部调度。

## 14. 恢复上线

1. 启动其余节点，每个节点使用唯一的 CHANNEL_MONITOR_CONSUMER_ID。
2. 确认所有节点连接同一个 MySQL 和 Redis 逻辑库。
3. 恢复入口流量。
4. 持续检查错误日志、Redis pending、清理任务状态和新表增长速度。

## 15. 失败和回滚

任何步骤失败都保持停机，不恢复流量。

需要回滚时，恢复上线前 MySQL 备份和 Redis 上线前快照，部署旧版本后再启动。不要执行 FLUSHDB、FLUSHALL、PURGE BINARY LOGS 或本文之外的删除命令。
